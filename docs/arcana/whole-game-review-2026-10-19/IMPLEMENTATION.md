# Plan ejecutable para una fase posterior

Esta fase **no implementa**. Los pasos describen cómo transformar la revisión en cambios revisables, no tareas parcialmente hechas. No hace falta aprobar todo el backlog para abordar el primer recorrido.

## Incremento recomendado primero: meta verdadera y recuperación en contexto

**Inicio:** consultar Atlas/Cromodex y bóveda en una cuenta existente. **Decisión:** qué objetivo sigue disponible y cómo continuar si la sesión caduca. **Cierre:** mismo jugador, recursos reconciliados y una acción viable. U01/U02/U03 son el núcleo; U04/U05/U14 acompañan únicamente los consumidores afectados.

1. Contrato de completitud: leer readmodel de colección y definir vigentes obtenibles frente a archivo. Modelo puro compartido por JourneyCabinet/CollectionPanel. Pruebas que fallen con catálogo30/34, archivo, criatura, repetido y encantado. No nuevo campo persistido por conveniencia de UI, no magicnumber34.
2. Proyección de bóveda: usar stock y derechos autoritativos existentes. Antes de primera llave, con llave, después de consumo y victoria repetida. Si un dato no existe en readmodel, añadir mínimo read-only sin alterar derecho ni escanear receipts completos por render. CTA a fuente solo si alcanzable; sino colección/plan disponible.
3. RecoveryNotice/App: acceso a cuenta existente desde aviso, dueño/pending guardados. Una intención incierta se resuelve o permanece bloqueada para otro propietario. No nuevo kit ni cuenta silenciosa. Pruebas previas a UI de sesión expirada, respuesta perdida y reautenticación misma/distinta.
4. Error de Halloween mediante operationErrorKey/adaptador y mensajes ES/EN, sin copiar mensajes técnicos. Cierre resiliente en ShopBook/CollectionPanel/FlavourCabinet, reutilizando patrón local de fallback. La X no dispara operación.
5. Evidencia seleccionada Linux de estas ramas, regresiones de identidad, cierre y colección. Real PostgreSQL/Redis si se toca gateway/readmodel/recuperación; no basta snapshotDOM.

**Archivos probables:** JourneyCabinet.tsx, CollectionPanel.tsx, CommercePanel.tsx, RecoveryNotice.tsx, App.tsx, SeasonalEvent.tsx, ShopBook.tsx, FlavourCabinet.tsx, messages por pack y modelo compartido de proyección. Confirmar consumidores con búsqueda antes de editar; no tocar motor de combate.

**Aceptación de salida:** mismos totales de identidad y porcentajes≤100, ninguna llave prometida sin derecho, login vuelve al mismo jugador, consulta/cancelación no consume, operación perdida se recupera una vez, cerrar es visible sin arte, ES/EN/pack/teclado/reducido coherentes.

## Estrategia de control de cambios

Commits futuros por recorrido, con cambios mínimos y test de riesgo antes de corregir. Migraciones solo si persiste un requisito real; previsión actual de U01/U02 es proyección, no inventario duplicado. Sin dependencia nueva prevista. Rama/PR/merge requieren el alcance que se autorice entonces; este documento no hace push ni autoriza publicación.

Rollback técnico futuro: revertir presentación/proyección por commit preservando esquema aditivo si lo hubiera; nunca restaurar una base para deshacer UI ni borrar receipts. Si una muestra necesita reglas nuevas, separar propuesta y entregar la variante compatible.
